# Hospital Communication Hub — 要件定義書

最終更新: 2026-09-22 / 状態: Phase 1（UIプロトタイプ）着手

## 1. 目的

院内職員が毎日使えるチャットを入口に、院内業務（お知らせ・ナレッジ・機器トラブル報告・安否確認・
アンケート）を1つのWebアプリにまとめる。LINE並みの学習コストで、説明なしに使えることを最優先とする。

## 2. 利用者

| 区分 | 想定 | 主な使い方 |
|---|---|---|
| 一般職員 (USER) | 医師・看護師・臨床工学技士・コメディカル・事務 | チャット、マイルーム、ノート閲覧、ナレッジ検索、トラブル報告 |
| グループ管理者 (GROUP_ADMIN) | 部門のリーダー | グループ作成・メンバー管理・重要メッセージ化 |
| 部門管理者 (DEPARTMENT_ADMIN) | 師長・室長クラス | お知らせ配信、アンケート、部署管理 |
| システム管理者 (SYSTEM_ADMIN) | 情報システム担当 | ユーザー・権限・施設・監査ログ・システム設定 |

## 3. スコープ（今回の成果物 = Phase 1）

バックエンドは作らない。モックデータで実際に操作できるフロントエンドプロトタイプ一式。

### 3.1 実装する画面

| ルート | 画面 | 必須の操作 |
|---|---|---|
| `/login` | ログイン（デモ用アカウント選択つき） | ログイン／権限の切り替え |
| `/groups` | グループ一覧（アプリの中心） | 一覧表示・未読バッジ・ピン・ミュート・非表示・検索 |
| `/direct` | 個人（DM）一覧 | 同上＋新規DM開始 |
| `/chat/:id` | チャット画面 | 送信・返信・リアクション・編集・削除・保存・ピン・重要メッセージ化・既読・AI要約・ルームメニュー |
| `/chat/:id/note` | 共有ノート | Markdown表示・編集・バージョン管理・更新履歴 |
| `/menu` | メニュー（ダッシュボード） | タイル遷移・お知らせ表示 |
| `/myroom` | マイルーム（自分専用チャット） | メモ・TODO・URL・ファイル保存 |
| `/knowledge` | 院内ナレッジ検索 | 横断検索・カテゴリ絞込・本文表示 |
| `/trouble` | 機器トラブル報告 | 新規報告フォーム・一覧・詳細・指定グループへ自動投稿 |
| `/announcements` | お知らせ | 一覧・既読・詳細（作成は DEPARTMENT_ADMIN 以上） |
| `/safety` | 安否確認 | 回答フォーム・回答状況（管理者） |
| `/surveys` | アンケート | 回答・結果閲覧 |
| `/admin` | 管理画面（PC前提） | ダッシュボード・ユーザー・部署・グループ・お知らせ・アンケート・安否・監査ログ・設定 |

### 3.2 必ず動くこと（受け入れ条件）

1. ボトムナビ3タブ（グループ／個人／メニュー）で相互に移動できる
2. チャット一覧から部屋を開き、メッセージを送信すると即座に一覧の最終メッセージと時刻が更新される
3. 未読バッジが表示され、部屋を開くと消える
4. ピン留め・通知OFF・非表示が一覧に反映され、リロードしても保持される
5. 一覧とチャット内でテキスト検索ができる
6. AI要約モーダルが開き、未読件数に応じた要約が構造化されて表示される
7. 重要メッセージ（緊急／重要）が通常メッセージと明確に区別され、「確認しました」で確認人数が増える
8. AIの発言が人間の発言と一目で区別できる
9. 権限を切り替えると表示される機能が変わる
10. スマホ幅（375px）／タブレット／PC幅で破綻しない

## 4. 非機能要件

- 最小フォント14px、本文15〜16px、タッチターゲット44px以上、WCAG 2.1 AA のコントラストを意識
- 外部CDN・外部フォント・解析タグへの通信を持たない（院内配布を想定し、依存はすべてバンドル）
- 将来PWA化できる構成（ルーティング・状態・データ取得の分離）
- モバイルファースト。PCでは一覧＋本文の2ペイン

## 5. 前提・決定事項（設計書からの変更を含む）

| # | 内容 | 理由 |
|---|---|---|
| P1 | Phase 1 ではデータ取得を `repository` 層に隔離し、実装はモックのみ | Phase 3 で Supabase でも院内PocketBaseでも差し替えられるようにするため。院内閉域網では Supabase（クラウド）に接続できない可能性があり、バックエンドを今決め打ちしない |
| P2 | shadcn/ui はCLIで導入し、コンポーネントは自プロジェクト所有 | 設計書の指定どおり。配色は院内トークンで上書き |
| P3 | 状態は Zustand ＋ localStorage 永続化 | バックエンド不在でも操作結果が残り、プロトタイプとして評価できるため |
| P4 | モックデータは `src/data/*.json`。基準日 2026-09-22 の ISO 時刻で持ち、読み込み時に当日へ日付をずらす | いつデモしても「今日」の会話に見えるため |
| P5 | ダークモードは配色のみ用意し、既定では使わない | 設計書の対象外。壊れた見た目を防ぐための保険 |
| P6 | 画像添付はダミー（説明文つきプレースホルダ） | バックエンド不在。実ファイルを同梱しない |
| P7 | 設計書 §24 の画面に加えて `/safety` `/surveys` `/chat/:id/note` `/ai` を独立ルート化 | §12・§13・§16 の機能に到達する導線が §24 に無かったため |
| P8 | 設計書 §21 の Danger / Warning / Success / Sub text を、文字・塗り用に一段暗くした | 元の色は白文字・小さい文字で WCAG AA（4.5:1）に届かない。§22 の「AA を意識」を優先し、罫やアイコンには元の色を `*-accent` として残した |
| P9 | 設計書 §10 の「機器管理」タイルは作らず、「AI アシスタント」を独立画面にした | 機器管理は機器トラブル報告と役割が重複し、見た目だけの画面になるため（§26） |

## 6. 医療・個人情報の扱い（厳守）

- 実在の患者情報・職員情報は一切使わない。すべて架空のテストデータ
- 臨床的な数値・手順・機器設定・薬剤名をAIが創作しない。モック会話は運用連絡（時間・担当・準備物）の
  範囲にとどめ、臨床判断に読めるものを書かない
- アプリ内に「デモ用ダミーデータ。臨床判断には使用しない」旨の表示を置く

## 7. スコープ外（Phase 2 以降）

認証基盤・DB・リアルタイム同期・ファイルアップロード・プッシュ通知・AI(RAG)実接続・監査ログの実運用。
